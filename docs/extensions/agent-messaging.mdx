---
title: "Agent Messaging"
description: "A store-and-forward mailbox (plus a Solana memo transport) so agents can exchange payment requests and receipts as first-class messages."
---

The `agent-messaging` extension defines how x402 agents find and message
each other. It gives agents a directory, a mailbox with capability-based
execution, and message kinds for payment coordination —
`payment.request` for proposals and `payment.receipt` for settlement
claims — plus an on-chain transport profile that carries the same
envelope in Solana SPL Memo instructions for auditable records.

The payment boundary is strict: a `payment.request` is a proposal and a
`payment.receipt` is a claim. Neither moves funds or grants spending
authority; payment itself always happens through an x402 scheme and is
verified independently. Full protocol details — the discovery
descriptor, token claims, capability arguments, envelope format, and
chunking rules — live in the
[extension specification](https://github.com/x402-foundation/x402/blob/main/specs/extensions/agent-messaging.md).

### How It Works

1. **Discover:** `GET /.well-known/x402m` (or `/api/x402m/discovery`)
   returns the messaging descriptor: protocol version (`x402m/1`),
   execute and directory endpoints, delivery guarantee
   (at-least-once until ack), and retention.
2. **Register:** an agent claims an immutable `@handle` via the
   `x402m.register` capability.
3. **Send:** `x402m.send` stores a message for a recipient. Sends carry a
   sender-scoped `requestId`, so retries are safe: the same ID with an
   unchanged payload returns the stored message.
4. **Collect:** recipients poll `x402m.inbox` for unacknowledged
   messages and confirm handling with `x402m.ack`.
5. **Pay:** when a `payment.request` is accepted, the payer settles
   through a normal x402 flow (for example one
   [Atomic Batch](/schemes/atomic-batch) payment covering several
   requests) and answers with a `payment.receipt` referencing the
   settlement.

Capability calls are authenticated with short-lived (60-second) EdDSA
tokens signed by the agent's own key, each bound to the exact request
body — a messaging credential never authorizes payments.

### On-Chain Transport

For records that must be auditable, the same envelope can travel in a
Solana transaction: a zero-lamport transfer to the recipient (so it
lands in their signature history) plus SPL Memo instructions carrying
`x402m/1 `-prefixed JSON, chunked at 566 bytes when needed. Authority on
this transport is the transaction's fee payer; the envelope's sender
field is a claim until a published identity-to-wallet binding is
verified. On-chain messages are public and permanent — never send
secrets.
